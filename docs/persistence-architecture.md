# Persistence architecture

Status: implemented on branch `fix/postgres-persistence`. Not deployed.

## Decision

Kidcellence stores all platform records in Postgres, provided by **Netlify
Database**. Netlify Blobs now holds only uploaded files.

Postgres is used through the `@netlify/database` package (pinned to 2.0.1). Locally
and in tests, `PLATFORM_DATABASE_URL` points it at any Postgres server.

## Why the previous design lost data

On 2026-11-10, a test on deploy preview #3 sent concurrent requests to the
single-JSON-document store in Netlify Blobs. It lost writes that it had already
acknowledged with HTTP 200:

- 3 of 20 sign-ups
- 7 of 21 messages
- 15 of 40 page views (12 of them with no logged failure)

Provider analytics counted messages that were not in the store. That means
writes reported as committed were later overwritten.

**Confirmed:** In `@netlify/blobs` 10.7.13, a conditional `set`/`setJSON` returns
`{ modified: true }` for every response except 412. It also retries 429 and 5xx
responses up to 5 times, then returns the last response. So a conditional write
that finally fails with a 429 or 5xx is reported to the caller as a success.
This was confirmed by reading the SDK source.

**Not distinguished:** whether the losses came from that reporting gap, or from
the Blobs service accepting a stale `If-Match` (non-atomic compare-and-swap)
under concurrency. The losses fit either explanation. We stopped storing records
in Blobs, so the answer no longer decides the design, and it remains unresolved.

**Structural cause, independent of either hypothesis:** every write rewrote one
document holding all users, sessions, messages and profiles. Correctness
depended entirely on an optimistic compare-and-swap that we could neither verify
nor observe. A single misreported write therefore silently discarded other
users' changes.

## Options considered

| Option | Verdict |
|---|---|
| Fix the Blobs implementation (treat non-success statuses as failures, verify after write) | Rejected. It would close the reporting gap only. Atomicity of `If-Match` on the service stays unproven, there are no multi-record transactions, and every write still serialises through one document. |
| Independent records in Blobs (one blob per user or message) | Rejected. Appends stop colliding, but shared records (unread counters, verification state, uniqueness of emails) still need the same unverified compare-and-swap, and there is no way to update two records atomically. |
| Cloudflare D1 (`feat/stripe-billing-and-d1`) | Rejected for now. It needs a Cloudflare account, API credentials and a proxy Worker, because the D1 REST API is rate limited account-wide. That branch's driver also reads the whole store and writes changed rows with no transaction or lock, so shared-row lost updates remain. |
| Supabase or another external Postgres | Viable. It needs a new external account and credentials managed outside Netlify. |
| **Netlify Database (Postgres)** | **Chosen.** Real transactions and constraints. Already available on the site's Pro (credit-based) plan, with no new account and no credentials to manage. Each deploy preview gets its own database branch. Migrations run in the deploy lifecycle, with daily and on-publish backups. |

**Netlify Database cost.** It consumes Netlify credits:

- Compute: 10 credits per unit.
- Bandwidth: 20 credits per GB.
- Storage: free until 2026-07-01 according to Netlify's docs, and that date has passed, so confirm current pricing before relying on it.

The Pro account includes 3,000 credits per month. Netlify states the service is
not PCI-DSS certified. Kidcellence stores no card data (Stripe hosts payment
pages).

## How writes stay correct

The design keeps the application's existing data model and all of its business
logic in `lib/platform-store.ts`. Only the storage layer underneath changed.

1. **Schema** (`netlify/database/migrations/0001_platform_store.sql`).
   - **Tables:** one table per collection (users, sessions, messages and so on).
   - **Full record:** each row keeps the complete application record in a JSONB
     `data` column, so nothing is lost in translation.
   - **Integrity columns:** identity and integrity columns are generated by
     Postgres from `data`, so they can never drift from it. Constraints:
     - unique normalised email
     - valid roles and statuses
     - session → user and account token → user foreign keys
     - message → conversation foreign key
     - one conversation per parent and provider listing
     - unique `(conversation, sender, clientMessageId)`
2. **Serialised read-modify-write** (`lib/store-postgres.ts`). Every `updateStore`
   call runs in one transaction that:
   1. takes a transaction-scoped advisory lock shared by all writers;
   2. loads the current state;
   3. runs the existing updater;
   4. writes only the rows that changed;
   5. commits.

   Two writers can never compute from the same stale state, so a lost update is
   impossible by construction rather than by retry.
3. **Acknowledgement after commit.** A route answers 200 only after `COMMIT`
   returns. Any failure before that rolls back the whole transaction.
4. **Analytics.**
   - **Page views:** platform analytics use their own row lock, so page-view
     traffic never waits on account or message writes.
   - **Message analytics:** messages and their provider analytics commit in the
     same transaction, so counts always match the stored records.
5. **Idempotency.**
   - **Messages:** a message carrying a `clientMessageId` is stored once
     however often it is retried. The messages page sends one, and reuses it
     when the user retries a failed send.
   - **Sign-up:** repeating a sign-up with the same password logs in instead of
     creating a second account.
   - **Payments:** recording a verification payment for an already-paid profile
     returns the existing record.
6. **Explicit failures** (`lib/persistence-errors.ts`). Every API route maps
   storage failures to explicit responses:

   | Failure | Response |
   |---|---|
   | Database unreachable or not yet initialised | 503 `STORE_UNAVAILABLE` |
   | Lock not acquired within 8 s, or statement timeout | 503 `STORE_BUSY` |
   | Constraint rejected the change | 409 `STORE_INTEGRITY` |

   Page-view and profile-view endpoints no longer answer `ok` when nothing was
   saved.
7. **Initialisation gate.** The database serves data only after it has a data
   source marker: either a completed import of the legacy store, or (outside
   production, when `PLATFORM_DATABASE_ALLOW_EMPTY_INIT=true`) an empty start.
   A production deploy that lands before the import therefore answers 503. It
   never shows an empty site and never accepts writes that would collide with
   the import.
8. **Failure handling.**
   - Connection acquisition times out after 5 s.
   - Transactions have lock, statement and idle-in-transaction timeouts, so an
     instance frozen mid-transaction cannot hold the lock for long.
   - Deadlocks and serialisation failures retry the whole transaction (at most 3
     attempts).
   - A connection dropped by the server while checked out is reported as
     unavailable instead of crashing the process.

## Limits and when to revisit

- **Throughput ceiling.** All store writes are serialised. Each write loads the
  whole store in one query. That is comfortably fast at today's scale (tens of
  users), and page views are not serialised with it.

  Revisit when either of these holds:
  - p95 write latency exceeds about 500 ms;
  - the store grows past roughly 5,000 users or 50,000 messages.

  The next step is to move hot paths (sign-up, message append) to targeted SQL
  that does not load the whole store. The schema already supports that.
- **Unbounded lists.** These grow without limit, as before:
  - `sessions`
  - `revoked_session_tokens`
  - analytics `visitorIds`
- **Preview data.** Deploy-preview database branches start as a copy of
  production data. After cutover, previews contain copies of real personal data.
- **Local file store.** It remains for development, with a cross-process lock and
  atomic writes. Its analytics are recorded after the main write (best effort).
  Deployed environments never use it.
- **Out of scope.**
  - **Bookings:** there is no booking backend on `main`, so there is nothing to
    persist. No booking feature was added.
  - **Payments:** on `main` they are Stripe Payment Links with no webhook, so
    paid status is never recorded automatically. That is a pre-existing product
    gap, not a storage one. The webhook on the D1 branch should record each
    Stripe event id once (a unique key) when it is ported.

## Local development

- `npm run dev` without a database uses the local JSON file store (`data/`).
- To develop against Postgres, set `PLATFORM_DATABASE_URL` to a local server
  and `PLATFORM_DATABASE_ALLOW_EMPTY_INIT=true`, then apply the migration.
- The test harness in `scripts/test-support/postgres.mjs` starts a disposable
  PostgreSQL 17 server from the `embedded-postgres` dev dependency.
